# Коротко для защиты

## Что сделано — рассказ на минуту

Я дополнил шаблон на C++17 и сделал подсистему измерения качества UDP-соединения.
Клиент каждые 200 мс отправляет PING с номером и временем отправки.
Сервер возвращает PONG с той же меткой и двумя своими метками для диагностики.
Клиент вычитает своё время отправки из своего времени приёма и получает RTT.
По успешным ответам вычисляются сглаженный RTT, джиттер, минимум, максимум,
среднее и медиана. Если ответа нет 1 секунду, измерение считается потерянным.
Дубли, поздние ответы, неверные пакеты и неизвестные номера обрабатываются отдельно.
Я провёл 6 серий по 50 реальных UDP-запросов и сохранил CSV, графики и отчёт.

## Как устроен код

| Модуль/файл | Ответственность |
|---|---|
| src/protocol.cpp | преобразует числа в байты big-endian и проверяет входной пакет |
| src/transport.cpp | открывает/закрывает UDP-сокет, отправляет и принимает датаграммы |
| src/telemetry.cpp | хранит ожидаемые запросы и вычисляет метрики без сетевых вызовов |
| src/client_main.cpp | связывает модули, соблюдает расписание, пишет CSV |
| src/server_main.cpp | принимает PING и планирует PONG без блокирующего sleep |
| include/app/emulation.hpp | воспроизводимые задержки/потери по seed |
| scripts/run_experiments.py | запускает настоящие клиент и сервер для 6 серий |
| scripts/analyze.py | независимо пересчитывает метрики из CSV и строит графики |

Разделение позволяет тестировать расчёты с искусственно заданным временем,
без реальной сети и ожидания тайм-аутов. Сетевой обмен проверяется отдельными тестами.

## Формулы и пример

- RTT = время приёма PONG клиентом − время отправки PING клиентом.
- Первый SRTT равен RTT; дальше SRTT = 0.875 × старый SRTT + 0.125 × RTT.
  Например, для RTT 50 и 100 мс получим SRTT 50 и 56.25 мс.
- Джиттер — среднее |RTT текущего ответа − RTT предыдущего успешного ответа|.
  Для RTT 50, 100, 50 мс это (50+50)/2 = 50 мс.
- Потери = число тайм-аутов / число отправленных PING × 100%.

## Что спросят

**Зачем свои часы клиента?** Часы сервера и клиента могут не совпадать.
steady_clock монотонный и не меняется при переводе системного времени.

**Зачем номер и исходная метка?** Номер сопоставляет ответ с запросом.
uint16 после 65535 повторяется, поэтому дополнительная метка отсеивает старый ответ.

**Что с поздним ответом?** После 1000 мс записывается timeout. Первый поздний PONG
даёт late_response, но потеря сохраняется. Следующий такой PONG — duplicate_response.

**Как проверяется пакет?** Тип, версия, длина заголовка и payload, границы буфера.
Неправильный пакет отбрасывается и логируется. Сырые C++ struct в сеть не копируются.

**Что показал эксперимент?** Baseline около 0.20 мс; при +50 мс получено 50.50 мс,
при +100 мс — 101.12 мс. Jitter и combined дают заметные колебания.
При вероятности потерь 5% фактически потерян 1 из 50 ответов (2%) в каждой
серии с потерями: 5% — вероятность, а маленькая выборка даёт случайный результат.
Задержку добавляет сам сервер; это честно указано, это не замер интернета.

**Что проверяли тестами?** Точные байты PING/PONG, обрезанные/неверные пакеты,
SRTT и джиттер на известных числах, deadline, дубли, поздние ответы,
старую метку, переполнение истории, реальные сокеты и неверные CLI-параметры.

**Где Git-процесс?** Ветка feature/latency-measurement, отдельные коммиты,
issues и Pull Request в GitHub. Исходная история GitVerse сохранена.
Автоматизированное ревью выполнено; ревью участника команды нужно отдельно.

## Как показать запуск

Из pr2-latency-template выполнить сборку из README, затем в двух терминалах:

```bash
./build-release/server 127.0.0.1 27015 baseline 20261020
./build-release/client 127.0.0.1 27015 defense 50 200 docs/defense.csv
```

Для тестов: `ctest --test-dir build-release --output-on-failure`.
Для результатов открыть docs/Latency_Report.md.
